# 架构优化提案（2025-11-13）

## 背景
Argo 目前以单进程、单实例的方式驱动 go-rod 浏览器完成目标站点的动态爬取。随着需求扩展（多目标并发、可插拔登录/脚本策略、云端部署），现有高度耦合的 Engine 体系在可维护性、扩展性和资源控制方面逐渐暴露瓶颈。本文梳理现状痛点并提出可落地的架构优化方案与实施计划。

## 现状痛点
1. **全局状态耦合**：`ResultList`、`Normalizeation*Map`、`urlsQueue`、`tabQueue` 等通过包级变量共享，导致无法在同进程安全运行多个目标，测试与复用困难。
2. **调度与背压缺失**：URL 队列容量设置为 1e7，无优先级与速率控制，极端站点易造成内存膨胀；Tab 并发受限于手写信号量，缺乏可视化与动态调整能力。
3. **巨型函数与职责混杂**：`engine.NewTab` 负责浏览器生命周期、流量劫持、DOM 解析、自动触发、结果入库，代码超过 300 行，新增策略需穿插多处逻辑，风险高。
4. **交互策略难以扩展**：自动登录、PlayBack、JS 注入通过硬编码顺序调用，缺乏统一插件接口，也不能按站点自定义启停或插拔新策略（验证码、人工介入等）。
5. **输出与观测薄弱**：结果仅落本地文件，缺少结构化 sink 与运行指标；异常（404 相似度、Tab Timeout 等）无法集中观测或复盘。

## 优化目标
- **并发隔离**：允许同进程并发扫描多个目标，每个 Target 拥有独立状态与资源配额。
- **弹性调度**：引入具备背压、优先级、速率控制的 URL 调度器，并可根据站点特性调节策略。
- **模块解耦**：将 Fetch、Interact、Extract、Sink 等责任拆分，并定义中间件式扩展点，降低跨模块影响。
- **可插拔交互**：提供统一接口注册自动化策略，便于定制脚本、验证码处理、人工注入等能力。
- **可观测可复用**：结果输出支持多通道（文件/JSONL/队列），同时暴露运行指标与事件日志，便于运维与测试。

## 优化方案
### 1. Engine 上下文封装
- 引入 `engine.Engine` 结构体，将 `ResultList`、`NormalizeStore`、`Scheduler`、`Sink`、`Interactions` 等组件作为字段，由 `cmd/argo` 为每个 target 构建独立实例。
- 使用 `context.Context` 贯穿 Engine 生命周期，统一超时、取消与资源清理。
- 拆分 `InitEngine`，实现 `NewEngine(config TargetConfig) (*Engine, error)` 和 `Engine.Run(ctx)`，便于单元测试与多目标并行。

### 2. 调度器与背压
- 设计 `Scheduler` 接口（`Submit`, `Next`, `Stats`），默认实现基于 worker 池 + 优先队列（按深度、来源排序）。
- 将 `urlsQueue` / `tabQueue` 替换为 Scheduler，提供最大队列长度、速率限制、失败重试策略，并在队列满时丢弃或降级。
- Tab 池改为 `WorkerPool`（可配置并发、空闲超时），统一记录活跃/空闲资源。

### 3. Pipeline 化的 Tab 处理
- 将 `NewTab` 拆为 `fetch.PageSession`（负责 rod Browser & Hijack）、`extract.StaticExtractor`、`extract.DynamicExtractor`、`sink.ResultWriter` 等独立模块，以管道/中间件串联。
- 通过中间件接口允许在请求前/后注入逻辑（脚本注入、登录检测、Playback、指标采集）。
- 为流量劫持与 Normalize 增加事件通道，便于外部模块订阅。
- ✅ 已提供 `PageMiddleware` 注册器与 `auto.middlewares` 配置，内置 `static/interaction/metrics`，支持按顺序启停并新增自定义中间件。
- ✅ URL 去重逻辑升级：path/查询参数按段归一化（数字→`{num}`、UUID→`{uuid}`…），参数顺序与大小写统一，method/scheme/host 纳入 key，并设置 50 万条缓存上限，避免误判与内存膨胀。

### 4. 交互插件框架
- 定义 `type Interaction interface { Name() string; CanHandle(*PageContext) bool; Execute(context.Context, *PageContext) error }`。
- 提供默认插件：LoginAuto、PlaybackRunner、AutoJS、CustomScript；通过配置决定启用顺序与参数。
- 允许用户在 `configs` 中声明额外脚本/插件，未来可扩展为动态装载。
- ✅ 现版本已提供 `auto.interactions` 配置与注册表，login/playback/auto 以插件形式运行，可按顺序启停。

### 5. 结果输出与观测
- 抽象 `Sink` 接口（`Write(*Result)`、`Close()`），默认实现 FileSink（txt/json/xlsx/html）与 StdoutSink (quiet)；预留 JSONL/消息队列实现。
- 在 Engine 与 Scheduler 暴露指标（成功 URL 数、404 判定、Tab Timeout、平均处理时间），写入 logrus 或 Prometheus 兼容输出（后续可拓展）。
- 将当前 `ResultHtmlData` 生成逻辑迁移到 Sink，以减少全局变量依赖。
- ✅ 已实现 txt/json/xlsx/html+jsonl sink，并新增 `--metricsfile` 输出 pages_processed/urls_dropped/tabs_timeout 等指标，默认日志也带摘要。
- ✅ 新增 `result.mq` 配置与 `mq` sink（HTTP POST），可将抓取结果推送到外部消息队列或自定义处理服务。

## 任务拆分（优先级高→低）
1. **Engine Context 重构（P0）**  
   - 新建 `engine/engine.go` 结构体，封装 config/state。  
   - 将 `InitEngine` / `Start` 拆分为实例方法，移除全局变量。  
   - 调整 `cmd/argo.go`，为每个 target 并发创建 Engine，并通过 `errgroup` 统一退出。
2. **Scheduler 与 Tab Worker（P0）**  
   - 引入 `scheduler` 包，实现带背压的 URL 队列和 Tab worker 池。  
   - 替换 `urlsQueue`/`tabQueue`/`TabLimit`，补充队列状态指标。  
   - 衔接 Normalize/Result 逻辑到新 Scheduler。
3. **Result Sink 抽象（P1）**  
   - 定义 `Sink` 接口，迁移 txt/json/xlsx/html 写入逻辑。  
   - 支持 quiet/stdout 模式无需积累 ResultList。  
   - 为 sink 引入基础单测，确保多格式输出一致。
4. **Interaction 插件化（P1）**  
   - 定义接口与注册器，迁移 LoginAuto / Playback / AutoJS。  
   - 为配置文件增加交互链声明，支持顺序/启用开关。  
   - 编写示例插件与测试。
5. **Pipeline 重构与中间件（P2）**  
   - 抽象 `PageSession`、`Extractor`、`Normalizer`、`Hook`。  
   - 将 `NewTab` 改为 orchestrator，按中间件顺序执行。  
   - 增加 metrics/event 上报。
6. **扩展输出与指标（P3）**  
   - 新增 JSONL/消息队列 Sink。  
   - 输出运行指标（tab 活跃数、URL 发现速率、404 相似度）到日志或 /metrics。  
   - 撰写运维文档。

> 注：P0/P1/P2/P3 仅代表优先级梯度，建议每个阶段结束后执行冒烟+回归测试，并更新 docs。
